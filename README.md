# Color Inventory

Локальный плагин Figma для инвентаризации цветов, которые реально стоят на макетах. Он собирает и очищает факты перед решением о новой палитре. Палитру он не проектирует.

Плагин появился на первом шаге обновления цветовой части Core 2.0. Дизайн-систему нужно было обновить в сжатые сроки и при ограниченных ресурсах. Репозиторий и Storybook лежат в закрытом контуре, в рабочей среде Cursor их нет. Доступна библиотека в Figma: компоненты, токены и Playground с новыми продуктовыми концептами. На этих макетах цвета применены хаотично: разные темы, подмена токенов и прямые HEX.

Целевая последовательность работы:

1. инвентаризация фактически используемых цветов;
2. формирование primitive-палитр;
3. проверка палитр на компонентах;
4. подмена компонентов в продуктовых макетах;
5. проектирование semantic-модели.

Плагин закрывает первый пункт. Сигнал, который от него нужен: много почти одинаковых синих не тащить в Core 2.0.

## Что он делает

Плагин смотрит только текущее выделение, не всю библиотеку и не каталог переменных. Он обходит выбранные фреймы и собирает видимые solid fills и strokes: HEX, прозрачность, число использований, fill или stroke, привязку (variable, style или hardcoded), имена слоёв и компонент.

Для instance берётся имя исходного main component, даже если instance переименован вручную. Если instance — вариант, берётся имя родительского component set. Для обычного фрейма берётся имя самого фрейма, например Page.

Перед анализом нужно вручную выбрать Light или Dark. Автоматическое чтение темы через variable modes возвращало `unknown`, поэтому выбор appearance обязателен.

Дальше цвета разбирает человек:

1. Выбрать Light или Dark.
2. Выделить frame.
3. Нажать Analyze.
4. Отметить строки и массово назначить группу командой Apply group.
5. Нажать Add / Update DB.
6. Повторить для остальных frames.
7. Открыть View database и проверить сводную базу.
8. Экспортировать Tokens JSON.

Рабочие группы: Gray, Cyan, Violet, Success, Warning, Danger, Incident. Можно ввести своё имя группы, например для цветов графиков. В строке статуса такие группы суммируются как Chart, а в данных, Suggested name и JSON сохраняют собственное имя.

Unassigned значит «решение ещё не принято». Такие цвета не попадают ни в базу, ни в Tokens JSON. Отдельный Ignore из-за этого убран.

Повторный анализ того же frame заменяет его предыдущий вклад, поэтому uses не удваивается. Совпадения с разных фреймов склеиваются по связке appearance + palette + role + HEX + opacity: uses суммируется, компоненты объединяются.

Suggested name считается после склейки и сортировки по светлоте:

`{appearance}/{palette}/{role}-{NN}`

Пример: `dark/gray/text-01`. Role — text, border, icon, surface или color. Это навигационное имя инвентаризации, не semantic-токен. Его можно поправить вручную; правка хранится в базе и уходит в экспорт. Номер `01` — самый светлый цвет внутри одной связки appearance + palette + role.

Переключатель Show all / Show unassigned управляет текущим разбором. В режиме Show unassigned уже назначенные строки скрываются с экрана, но остаются в данных и сохраняются через Add / Update DB.

## Что сохраняется

База лежит в `figma.clientStorage` и привязана к Figma Desktop и этому плагину. Переносимый архив — JSON.

| Экспорт | Что внутри |
| --- | --- |
| Export CSV | таблица текущего разбора |
| Export DB CSV | сводная база |
| Backup JSON | sources по node id, ручные назначения, правки имён |
| Import JSON | восстановление базы на другой машине или после сброса |
| Export Tokens JSON | только назначенные цвета, без Unassigned |

Tokens JSON повторяет Suggested name: `dark/gray/text-01` превращается в `color.dark.gray.text-01`. У каждого токена есть `$type: color`, описание с числом использований и компонентами, и `$value` в формате, который Figma импортирует нативно: sRGB, components, alpha и hex. Старые имена токенов в файл не попадают.

Clear DB после подтверждения стирает sources, назначения и Suggested names. Текущий анализ остаётся открытым как Unassigned.

## Как открыть

В Figma Desktop: **Plugins → Development → Import plugin from manifest…** и выберите `manifest.json` из этой папки. Окно плагина — 1080 × 816.

## История решений

Семнадцать итераций. Каждая закрывала конкретный сбой на реальных макетах.

### 1. Базовый сбор

Анализ выбранных frames: solid fills и strokes, HEX, opacity, uses, привязка к токену, имена слоёв, CSV.

### 2. Автоматические группы

Близкие цвета группировались в OKLab. По hue, chroma и именам токенов плагин пытался сам выделить Gray, Cyan и Violet.

Так делать нельзя: групп получалось слишком много, светло-фиолетовый смешивался с серым, jade и green попадали в cyan. Итоговый HEX не объясняет, зачем цвет стоит на макете. Темы, semantic-токены, overrides и hardcoded-значения давали шум. Из HEX нельзя восстановить архитектурный смысл.

### 3. Ручные группы

Автоклассификация заменена ручным назначением: Gray, Cyan, Violet, Success, Warning, Danger, Incident. Unassigned — решение ещё не принято, в результат не писать.

### 4. Локальная база

Результаты стали храниться в `figma.clientStorage`, с выгрузкой CSV и JSON. Первой сущностью хранения был именованный scan.

### 5. Контекст компонента

Плагин находит исходный main component у instance, даже если instance переименован. Появилась группировка по компонентам и редактируемый Suggested name.

### 6. Ignore

Появились исключения по id variable и style и отдельный JSON под будущее создание primitives. Позже Ignore убран: Unassigned уже исключает цвет из результата.

### 7. В базу попадает только разобранное

Сохраняются только цвета с назначенной группой. Можно просканировать целую Page, назначить Gray одной поверхности и записать в базу один цвет.

### 8. Tokens JSON

Экспорт переведён на DTCG-подобную структуру `color.global.gray.50`. Старые имена токенов отброшены. Uses и компоненты переехали в `$description`.

### 9. Appearance в имени

Формат стал `appearance/palette/role/NN`, например `dark/gray/text/01`. JSON повторял это имя: `color.dark.gray.text.01`.

### 10. Одна база вместо списка scans

Именованные scans оказались лишними: проще дописывать frames в одну базу. Внутри остались скрытые sources по Figma node id. Повтор того же frame обновляет его вклад. Кандидаты объединяются по appearance + palette + role + HEX + opacity.

### 11. Light и Dark выбираются вручную

Чтение appearance из variable modes давало `unknown`. Перед Analyze появился обязательный выбор Light или Dark. Ignore и связанный с ним тулбар удалены.

### 12. Массовое назначение

Отдельный dropdown на каждой строке был слишком медленным. Появились чекбоксы, выбор всех строк и Apply group. Табы-фильтры групп заменены постоянной строкой статуса: сколько кандидатов в Gray, Cyan, Violet, системных группах и Unassigned.

### 13. Скрытие разобранного

После Apply group обработанные строки скрывались, на экране оставались только неразобранные. Назначенные цвета при этом оставались в данных.

### 14. Режим обзора по желанию

Автоскрытие полезно не всегда. Появился переключатель Show all / Show unassigned: полный обзор или режим, где после Apply group видны только неразобранные строки.

### 15. Свои группы

Фиксированный список заменён полем, куда можно вписать свою группу, например цвет категории или графика. В статусе они суммируются как Chart. В Suggested name и JSON остаётся введённое имя.

### 16. Импорт в Figma без стороннего плагина

Строка `$value: "#HEX"` принималась не всеми импортёрами. Значение переведено на объект цвета: sRGB, components, alpha и hex. Файл импортируется нативно из Variables.

### 17. Role склеен с номером

Отдельная папка `text` / `surface` / `icon` в Figma оказалась лишней. Имя стало `dark/gray/text-01`, в JSON — `color.dark.gray.text-01`.

## Выводы

1. Близость цветов в OKLab не равна близости в архитектуре системы.
2. Инвентаризация собирает факты. Решение о палитре принимает дизайнер.
3. Контекст компонента и роль важнее одного HEX.
4. Unassigned достаточен, чтобы не тащить цвет дальше.
5. Скрытые sources нужны, чтобы повторный анализ не удваивал uses. В интерфейсе их быть не должно.
6. Формат экспорта задаётся следующим шагом: импорт в Figma Variables.
7. Инструмент стоит проверять на живых макетах и менять маленькими итерациями.
